## 1. Rules to adopt into the guidelines

**§1 What this is: Rule 2, Flat**
- **Glass is the system's, never ours.** "Flat" covers what we draw. Native macOS 26 chrome keeps its glass; we never call `.glassEffect()` and never use glass on cards or content. [macos-design-guide §2; swiftui liquid-glass]

**§2 Foundations: Type**
- **Archivo for what we draw, the system font for native chrome.** SF system text styles go in menus, toolbar, sidebar, alerts and standard controls. [macos-design-guide §4.1, §3.6]

**§2 Foundations: Tone**
- **Roles become asset-catalog colours.** Same names, with Any, Dark and High Contrast appearances. `--accent` becomes `AccentColor`; system controls keep system colours. [macos-design-guide §4.2]

**§2 Foundations: Hit targets and focus**
- **Hit targets by input, one switch.** Touch: 44px. Mac pointer: at least 28pt native, 24px web. Switch once at the root, and only when a Mac app needs density. [interaction-design Touch Targets, Desktop; HIG; WCAG 2.5.8]
- **Focus ring by platform.** Web keeps our 3px ring. Native keeps the system ring (accent colour, follows `.contentShape`). Focus never looks like selection. [macos-design-guide §3.2; accessibility-patterns]

**§2 Foundations: Motion (gate 4, guidance only)**
- **SwiftUI motion uses our tokens.** Scoped `.animation(_:value:)`, `.timingCurve(0.22, 1, 0.36, 1, duration: 0.2)`, transforms and opacity only, no `.bouncy`. Reduce Motion turns the flip into a crossfade. [swiftui animation-basics]

**§3 Card: States**
- **Hover adds emphasis, never information, and never moves the hit area.** The lift is a shadow, not a translate (A3-03). Focus shows whatever hover shows. [interaction-design Platform: Web; accessibility-patterns]
- **The hand cursor is for links only.** Buttons, selectable cards and disabled items keep the arrow, as on the Mac. No `not-allowed` cursor. [macOS HIG Pointers]

**Platforms: macOS (new section)**
- **Every command is in the menu bar, with a shortcut.** Standard ⌘ shortcuts behave normally. SwiftUI: `CommandMenu` and `.keyboardShortcut`. Web shell: its native menu, not only a JS keydown handler. [macos-design-guide §3.1–3.2]
- **Keys.** Tab between groups; arrows and Home/End within a list or grid (roving tabindex). Return opens; Space selects or presses; Escape cancels, closes, then clears the selection. [accessibility-patterns Keyboard as Foundation]
- **Don't depend on Tab.** By default, macOS tabs only to text fields and lists, and Safari and WKWebView skip links. Make shortcuts and arrows the main route, and set `tabFocusesLinks` in a WebKit shell. [macOS platform convention]
- **A collection is navigable or selectable, never both.** Navigable: link cards, with `aria-current` on the anchor. Selectable: click, ⌘-click and ⇧-click, via `listbox`/`option` or `List(selection:)`. [component-patterns Lists › Selection]
- **Context menus are shortcuts, not the only route.** Every item is also in the menu bar or a visible control. Right-click acts on the selection, selecting first. SwiftUI: `.contextMenu(forSelectionType:)`. [component-patterns Row Actions]
- **Drag only where it means something.** If cards reorder, give drag a keyboard path and Undo. Otherwise set `draggable="false"` on `.card__link`, or a click-drag picks up a URL. [component-patterns Drag & Drop]
- **Windows resize live.** Set a minimum window size and test at it and at full screen; cards already follow their container. SwiftUI: `.windowResizability(.contentMinSize)`. [macos-design-guide §3.3; swiftui layout]

## 2. Conflicts

1. **Glass.** The skill says to use glass cards, glass buttons and `.glassEffect(.regular.interactive())` (swiftui liquid-glass.md, "Card with Glass Effect"). We use rule 2: flat, no translucency, and `check.mjs` bans `backdrop-filter`. Recommendation: **keep ours** for everything we draw, and accept glass only as the system's own chrome. The macOS guide itself keeps glass for the navigation layer, not content, and cards are content.
2. **System type and colour.** The skill says to prefer system text styles, spacing and colours, and to brand through content (macos-design-guide §4.1–4.2). We use one custom family and our own roles everywhere. Recommendation: **keep ours for content, adopt the skill's for native chrome.** Platform convention ranks above our direction (brief precedence 1), and chrome set in Archivo reads as a web page in a window.
3. **Focus ring.** The skill says the macOS system ring (accent colour, follows the shape, §3.2). interaction-design's example is a 2px blue ring. We use a 3px ink ring with a 3px offset. Recommendation: **keep ours on the web**, where it is stronger than the example and passes AA on every tone. **Adopt the system ring in SwiftUI**, because users rely on it and it adapts to Increase Contrast and the accent colour.
4. **Density.** The skill says to offer "high information density options for power users" (interaction-design Desktop), and HIG macOS controls are about 28pt. We use 44px bars, rows and foot everywhere. Recommendation: **keep ours as the default now, and add the skill's later** as one switch at the root (fine pointer only, floor 24px). 44 is the PWA floor, and a density mode with no Mac screen to test it on is guesswork.
5. **Motion feel.** The skill says `.spring` for interactive elements and `.bouncy` for playful feedback (swiftui animation-basics). We use instant states now, and the `--ease-out`/`--ease-flip` curves at gate 4. Recommendation: **keep ours.** `.spring(duration: 0.2, bounce: 0)` or a matching `.timingCurve` is fine. `.bouncy` is decoration (rule 7).

## 4. Skill entries for "Skills we build with"

**swiftui-expert-skill**
- Load it: when writing or reviewing a native SwiftUI screen, or porting a token or component to Swift.
- Take: modern APIs (`foregroundStyle`, `clipShape(.rect)`, `Button` instead of `onTapGesture`); `@Observable` and private `@State`; layouts that don't assume their context (`ViewThatFits`, `containerRelativeFrame`, which correspond to our container queries); and, at gate 4, scoped `.animation(_:value:)` with transforms only.
- Ignore: its Liquid Glass recipes for content (glass cards, glass or tinted buttons), `.bouncy`, and its iOS-first defaults (44pt everywhere, no menus or windows). Mac conventions decide those.

**interaction-design (desktop side)**
- Load it: when specifying any interactive state, a list or grid, a keyboard path, drag and drop, or a menu.
- Take: the keyboard as the foundation (Tab between groups, arrows within, Escape/Return/Space), roving tabindex, list selection with ⌘ and ⇧, context menus as shortcuts, drag with a keyboard alternative and Undo, no hover-only information, and the feedback timings.
- Ignore: its example styling (2px blue ring, opacity for disabled, a translucent drag preview, a "shadow + scale" lift), because our tokens decide the look. Also ignore the theory chapters (ZUI, marking menus, Laurel).
