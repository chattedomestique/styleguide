Foundations

Layout

Small composable primitives that set space and flow and never colour. They are intrinsic: they wrap, shrink and re-flow on their own, so the same markup holds at 320px wide, at 200% text, and in a one-column phone or a four-column desk. Media queries are kept for one job, the app shell.

App shell

.app is a phone-width column, centred on larger screens, with the safe areas as padding on all four sides (landscape phones have side insets). .app__main is the region between the app bar and the dock; it keeps room for the dock and the home indicator.

<meta name="viewport" content="width=device-width, initial-scale=1, viewport-fit=cover">

<body>
  <div class="app">                      <!-- add data-wide for the 64rem column -->
    <header class="sticky-top safe-top">…</header>
    <main class="app__main">…</main>
  </div>
</body>

Stack, cluster and split

Stack

Vertical rhythm: every direct child is separated by --stack-gap (default --space-4). Set it with data-gap from 1 to 7 (the steps of the space scale), or set the property yourself.

Cluster

A horizontal run that wraps: buttons, tags, avatars. --cluster-gap defaults to --space-2; data-gap accepts 1, 3, 4 and 5; data-justify is between, end or center; --cluster-align defaults to center. Targets in a cluster keep at least 8px between them.

Split

One row: the first child grows and may shrink, the last sits at the end. A title and an action, a label and a value. The first child has min-inline-size: 0, so a long title wraps instead of pushing the action off the screen. The last child is flex: none (never squeezed, capped at the row's width), and the row wraps: when the title and the action cannot share a line, the action drops under the title as a whole instead of overlapping it (second row below).

Grid

As many columns as fit --grid-min (default 12rem), no media queries: repeat(auto-fit, minmax(min(100%, var(--grid-min)), 1fr)). The min(100%, …) is what stops a cell overflowing a 320px screen. --grid-gap defaults to --space-3. data-cols="2" | "3" | "4" forces that many equal columns and does not reflow: use it only for small, fixed content such as a keypad, never for cards.

Mind the last row. Three cards in two columns leave one alone on the second row, which reads as an afterthought. When the number of cards is small and known, make it one that fills the rows you expect (two or four for a phone's two columns), or decide the columns yourself with a container query.

Bleed and scroller

.bleed lets a child run edge to edge inside the padded app column, with a negative margin equal to the column's side padding. .scroller is a horizontal run with native scrolling and scroll-snap, for chips, thumbnails and month switchers: momentum, keyboard and assistive-technology scrolling all work for free. Give it role="region" and an aria-label so it can be found, and add .bleed so it runs to the edge of the screen.

The frame above is the screen. The label, the first filter and the line below start at the column's edge; the row of filters runs on to the edge of the screen, and the filter the edge cuts off says there is more. Never stop a scroller at a frame line inside the layout: a pill sliced by a line reads as a mistake. The peek is not guaranteed: at some widths and text sizes the edge falls between two items and the row looks complete, so when missing an item matters, let the row wrap (.cluster) instead. Scrolling is an enhancement; every item is also reachable with Tab.

Container queries, not media queries

A component cannot know how wide the page is. It is the same card in a phone's one column and in a desktop's four. So components ask for their own width: .card is a container (container: card / inline-size) and its parts use @container card (max-width: 18rem). .cq makes any element a container, so children can respond to it. Media queries are for the app shell only, and they are written in em so the breakpoint follows the reader's text size: the docs shell switches to two columns at 64em, which is 1024px at default text and 2048px at 200%. Lint warns on a px media query.

Squeeze the box. The card re-templates itself when it is narrower than 18rem (the value drops under the title), and the grid drops columns as cells reach their minimum. The page width never changes.

Sticky chrome and focus

.sticky-top is position: sticky; inset-block-start: 0 at --z-sticky. Any sticky or fixed bar must tell the page how tall it is, through --appbar-h (top) and --dock-h (bottom), both 0px until set. html turns them into scroll-padding-block with --space-3 of air, so a focused control scrolls into view clear of the bar rather than hidden behind it (WCAG 2.4.11). This site's own bar does it: .docs { --appbar-h: 2.75rem }.

.my-appbar { position: sticky; inset-block-start: 0; z-index: var(--z-sticky); }
:root      { --appbar-h: 3.5rem; }   /* the bar's height, so focus is never hidden behind it */

Sticky stops working inside an ancestor with overflow other than visible; keep overflow: hidden off the app column.

Safe areas

Notches, rounded corners and home indicators take space the page must not use. The four tokens read the device's insets, and are 0px where there are none:

Safe-area tokens and classes
Token or classHere, nowWhat it does
--safe-topenv(safe-area-inset-top, 0px). .safe-top pads the block start by it.
--safe-bottomenv(safe-area-inset-bottom, 0px). .safe-bottom pads the block end by it; .app__main reserves it.
--safe-left, --safe-rightThe side insets of a landscape phone. .safe-x pads both inline sides by max(var(--gutter), inset); .app does it too. Always all four sides, never just top and bottom.

They need viewport-fit=cover in the viewport meta tag, or the browser letterboxes the page and reports 0. The phone below simulates a notch and a home indicator by setting the two tokens on its frame (47px and 34px, a recent iPhone's insets: they are device pixels, so they do not grow with the text); the dashed bands are the insets, and the bar and the dock grow by exactly that much.

Rows that never wrap raggedly

A bar or a row of controls must not wrap into two uneven rows: two destinations and a lonely third read as a grid, not as the app's main places, and a label broken to fit says nothing. Such a row has a few complete layouts, richest first, and uses the first one that fits on one line. The Dock shows icons and words, then only the current destination's word, then icons alone. The Segmented control goes from one row to one option per line. Pagination turns Previous and Next into circles, then shows only the first, current and last page, then "Page 5 of 12". CSS cannot ask "does this fit?", so a small script measures: SG.fit, in src/js/05-fit.js, part of the core script.

SG.fit.register('.my-bar', {
  steps: ['labels', 'icons'],   // richest first; the last one is used when none fits
  measure: '.my-bar__list',     // what must not overflow (default: the element itself)
  parts: '.my-bar__label',      // optional: parts that must not overflow either
  attrs: ['aria-current']       // optional: re-check when these change inside it
})

It tries each step in turn, writes it to data-fit on the element, and keeps the first one in which nothing overflows. The element's CSS draws each step. For the measure to mean anything, the CSS keeps the row on one line while data-fit is set, so "does not fit" shows up as overflow instead of as a wrapped row or a broken word:

.my-bar[data-fit] .my-bar__list { flex-wrap: nowrap; }
.my-bar[data-fit] .my-bar__label { white-space: nowrap; }
.my-bar[data-fit="icons"] .my-bar__label { /* hidden visually; it is still the name */ }
  • It checks again when the element's size changes (a rotation, the reader's text size), when the fonts load, when a matching element is added, and when one of attrs changes inside it. SG.fit.update() checks everything now.
  • Without JavaScript there is no data-fit, and the element's own CSS fallback applies: the row wraps, or it scrolls. Write that fallback first.
  • Words stay in the page in every step, as the accessible names. Hide a label visually, never with display: none.
  • Use it only where CSS cannot decide. A layout that depends only on the element's own width is a container query. SG.fit is for "does this exact content fit at this text size".

Set the text to 200% in your browser and open the Dock page: the dock changes from words to icons as a whole, and never wraps.

Reflow at 320px and 200% text

WCAG 1.4.10 asks that content reflow with no sideways scroll at 320 CSS pixels, and 1.4.4 that text can reach 200%. The primitives are built for it, and npm run test:a11y checks every page at 320px, and at 390px with the root at 200%.

  • .grid cells have a min(100%, …) floor, so one column always fits.
  • .cluster wraps; .split's first child shrinks; .card--row moves its trailing value under the title.
  • Text sizes are rem and heights are min-block-size, so a control grows with its label instead of clipping it. Insets, icon-only controls and their targets are chrome and stop at their 100% size, so the words get the width (Chrome caps).
  • A bar or a row of controls never wraps into uneven rows: it switches its whole layout (above).
  • Only a .scroller, a code block and a wide table are allowed to scroll sideways, and each is a labelled, focusable region.

Add a primitive

  1. Put it in src/layout/layout.css inside @layer sg.layout, wrapped in :where() so an app can override it with a plain selector, no !important.
  2. Make it intrinsic: flex or grid with wrapping and min(); no media query.
  3. Expose knobs as custom properties with a default in the rule (var(--stack-gap, var(--space-4))) and, for a few presets, as data-* attributes.
  4. Set space and flow only. No colour, border or shadow.
  5. Use logical properties (margin-inline, padding-block) so right-to-left works.
  6. Document it here with a live demo, and check it at 320px and 200% text.
