Components

Field

A field is a control plus the words that make it usable: a label you can always see, a hint, an error that says how to fix it, and whether it is required. Every input, select, choice, slider and stepper sits in one.

When to use

Do

Give every control a visible <label>. Say "(required)" or "(optional)" in words. Put the format in a hint ("Day, month, year") and keep the placeholder for an example at most.

Don't

Use a placeholder as the label (it vanishes when you type, so people forget what they were asked). Don't mark required fields with a lone asterisk or show errors in red alone.

Examples

Stacked, with a hint

The default: label above, hint under the label, control below. The hint is linked with aria-describedby so it is read when the field is focused.

As it appears on your bank card.

Required and optional, in words

A lone asterisk means nothing to a screen reader or to anyone who has not seen the form before. Write the word. If most fields are required, mark the optional ones instead, and say so at the top of the form. Also set the native required attribute so the browser can validate.

Inline layout

Label beside the control, for settings and wide forms. There is no media query: the two columns share the row while they fit and stack when they do not, so on a phone it is the stacked field again. Put the label and its hint in .field__head (the words) and the control in .field__body: stacked, that reads label, hint, control, exactly like every other field.

Where the order ships from.

Character counter

Add data-sg-counter to a .field__counter. The visible count updates as you type. A screen reader hears the count once, politely, when you pause typing, never once per keystroke. maxlength is a hard limit (the browser stops typing). data-sg-maxlength is a soft limit: you may go over, the counter says how far over in words and weight, and the field becomes invalid inside a validating form.

Error state

An error is three things at once: an icon, words that say what is wrong and how to fix it, and a second frame inside the control. Colour only reinforces. The message is linked with aria-describedby and the control carries aria-invalid="true". This is the server-rendered form of it, which needs no JavaScript.

Group: fieldset and legend

Radios and related checkboxes are a group. The <legend> is the group's label and is read before each option, so "Yes" is never heard without its question. The hint and error are linked to the <fieldset>.

Validation and the error summary

Put data-sg-form and novalidate on the form. Each field is checked when you leave it (only if it has a value, so tabbing past an empty field never makes the layout jump under your finger), then live while it shows an error. On submit, every problem is listed in the error summary, focus moves to it, and each entry is a link to its field. The summary is a card in the bad tone: frame, bar and ruled rows. Try it: press Send with the form empty, then fix the fields one by one.

    Forms and the standards

    A form is where most accessibility failures cost someone a booking, a payment or a sign-in. These are the WCAG 2.2 criteria that decide it, what the system does about each, and what is still yours to do.

    WCAG success criteria for forms and how this system meets them
    CriterionLevelWhat the system doesWhat you still do
    1.3.1 Info and relationshipsAReal <label for>, <fieldset> and <legend>; hint and error wired with aria-describedby.Group radios and related checkboxes in a fieldset.
    1.3.5 Identify input purposeAAThe attribute table lists the autocomplete token for each kind of data.Set the token on every field that asks about the person.
    1.4.1 Use of colourAError = icon + words + inner frame. Required = words. Selected = fill plus a mark.Never write "the red fields".
    2.5.3 Label in nameAThe accessible name starts with the visible label: the label is the name. Icon-only buttons (clear, show password, stepper) carry an aria-label that names the action in plain words.Do not aria-label a field with different words from the ones on screen.
    3.3.1 Error identificationAThe field is marked aria-invalid and the error is text next to it, in the summary, and in the field's description.Write the message (see below).
    3.3.2 Labels or instructionsAA visible label on every control; format goes in a hint before the control.Say the format and the units.
    3.3.3 Error suggestionAAdata-error-* per failure, so "how to fix" is authored, not the browser's generic text.Suggest the fix when you know it.
    3.3.4 Error preventionAAThe "checked" route: a form with data-sg-form does not submit until every field passes, and lists what to fix. sg:validated is the hook for a review step.For money, legal or deletion: offer review, confirm or undo before the final send.
    3.3.7 Redundant entryANothing in the system asks twice; autocomplete lets the browser fill what it knows.Carry answers across steps; offer "same as" (below).
    3.3.8 Accessible authenticationAAPassword fields allow paste and password managers; the show / hide button is a real toggle.Never block paste, never use a puzzle or a transcription test without an alternative (below).
    4.1.3 Status messagesAAThe summary is role="alert"; the counter speaks once after a pause; steppers and sliders announce the new value politely.Announce success with SG.announce().

    Redundant entry: “same as”

    If you already asked for it, do not ask again (WCAG 3.3.7). The usual case is a billing address that matches the delivery address. Offer a checkbox, leave it on, and only show the second set of fields when it is turned off, pre-filled with what was typed.

    Delivery address
    Billing address

    Accessible authentication

    Signing in must not depend on remembering, transcribing or solving something (WCAG 3.3.8). In practice: let the browser and the password manager fill the fields, allow paste everywhere (one-time codes too), keep the show / hide toggle, and offer a second way in that needs no recall: a sign-in link sent by email. No CAPTCHA puzzles; if you must prove a person is present, use a method that does not test cognition.

    Error prevention for money

    For anything that moves money, signs something or cannot be undone (WCAG 3.3.4), make at least one of these true: the last step is a review of what they entered, it can be reversed (and Undo is shown), or it is checked and confirmed before it is final. A review screen that repeats the amount and the recipient beats a "Are you sure?" dialog, which people click through. See the keypad for an amount entry.

    Writing the words

    How to write labels, hints and error messages
    PartRuleExample
    LabelA noun, short, in natural case. Never a question the placeholder answers.Email
    HintWhat format or where to find it. Before the control, so it is read first.Day, month, year. For example 14 3 2026
    ErrorWhat is wrong and how to fix it. Plain words, no blame, no error codes.Enter a date like 14 Mar 2026
    Summary entryThe same sentence as the inline error, so the link and the field agree.Enter an email like you@example.com
    CounterRemaining, then "over" in words when exceeded.12 characters left / 3 characters over

    Anatomy

    1. Label (.field__label): always visible, a real <label for> (or <legend> for a group). Semibold, sentence case: it is text you read, not structure.
    2. Required / optional (.field__req, .field__opt): words inside the label, so they are part of its accessible name.
    3. Hint (.field__hint): secondary text, 7:1. Listed in aria-describedby.
    4. Control: input, select, choice, switch, slider or stepper.
    5. Foot row (.field__foot): the error on the start side, the counter on the end side. It takes no room while both are hidden.
    6. Error (.field__error): icon + message in --bad-ink, shown only while the field is in error. The message wraps in balanced lines, so an example address written with a <wbr> after its @ and after its dot moves to the next line whole when it fits there, and splits at those points only when it must.
    7. Error summary (.card.error-summary, data-tone="bad"): at the top of the form; a bar with the heading, one 44 px link row per problem.

    API

    Field classes and attributes
    AttributeValuesEffect
    class="field"on div or fieldsetGrid of label, hint, control and foot. A fieldset.field loses its UA border.
    data-layoutinlineLabel beside the control; wraps to stacked when narrow.
    data-sizelg, on .field__labelThe heading of a group that holds several fields ("Delivery address"), so the legend outranks the labels inside it.
    data-sg-fieldTurns on 30-field.js for this field: ids, label for, aria-describedby (error id only while visible), counter.
    data-sg-formon <form novalidate>Validate on leave, live after an error, everything on submit; fills and focuses the summary.
    data-sg-summaryon .card.error-summaryWhere the summary is written. Keep hidden, tabindex="-1" and a role="alert" child.
    data-sg-counteron .field__counterLimit from maxlength (hard) or data-sg-maxlength (soft). Words: data-left="{n} characters left", data-over="{n} characters over".
    data-error, data-error-missing|type|pattern|short|long|low|high|step|badtext, on the control or the fieldThe message for that validity failure. Falls back to the browser's own text.
    aria-invalid="true"on the controlBad-ink frame and inner frame. Set by you, or by SG.field. :user-invalid does the same after the person has touched the field.
    JavaScriptSG.field.setError(el, msg), .clearError(el), .validate(field), .validateForm(form), .showErrors(form, [{control, message}])Custom rules and server-side errors ("That email is already registered"). The event sg:validated is cancelable: cancel it to submit with fetch.

    Accessibility

    Field keyboard and screen reader behaviour
    InteractionBehaviour
    TabMoves between controls in reading order. The error summary has tabindex="-1", so Tab never stops on the box itself; script moves focus there after a failed submit, and Tab then walks the links inside it.
    Failed submitFocus moves to the error summary (tabindex="-1"); its role="alert" child announces the heading and entries. Tab then walks the links; Enter focuses the field.
    Screen reader, field"Email (required), edit text, invalid entry, Enter an email like you@example.com". Label, then name / role / state, then the description.
    Screen reader, groupThe legend is announced with each option: "How should we remind you, Email, radio button, 2 of 3".
    CounterAnnounced politely after a 1 s pause, not per keystroke. The visible count is in aria-describedby, so it is read on focus too.
    Hidden errorA hidden element that is referenced by aria-describedby is still read. The script therefore adds the error id only while the error shows.
    Not colour aloneError = icon + words + inner frame. A counter past its limit = words + bold. Required = words.
    Reduced motionNothing here moves.
    Forced coloursBorders are system colours; the error frame gets heavier (the inner frame is a shadow, which forced colours removes); the summary keeps its frame, bar and icon.
    No JavaScriptLabels, hints and native validation still work. Server-rendered errors are fully styled. You lose live validation, the summary behaviour and the counter.
    • Do not validate while someone is still typing their first answer, and do not clear their input on an error (WCAG 3.3.1, 3.3.3).
    • Errors must be reachable without a pointer: the summary links and the inline message cover keyboard and screen reader users.
    • The summary's live announcement and the focus move are the only announcements on submit. Inline errors are read when the field is focused, so they do not interrupt someone who is already moving on.
