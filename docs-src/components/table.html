Table

A table compares rows of the same kind of thing: transactions, decks, sessions. It is a real <table>, so screen readers can move cell by cell, inside a scroll region, so it never breaks the page at 320px.

When to use

Do

Use it when people compare values across rows or sort by a column. Put the row's name in the first column: it stays on screen while the rest scrolls.

Don't

Use a table to lay out a page, or for a list of one or two facts (use Card rows). Don't hide columns on small screens: scrolling loses nothing, hiding does.

Examples

Sortable, with a sticky first column

Sortable headers are buttons. The sorted column wears aria-sort, an arrow, and an underline, so the state never depends on colour. Amounts are right-aligned with tabular figures so the decimals line up, and negative amounts use the true minus (U+2212). The key value comes second, next to the name, so it is what a phone shows first. Click a header, or Tab to it and press Enter.

Empty

Say why there is nothing and what to do. The header stays, so the columns people would get are still visible. Put the sentence in a .tbl__empty-msg inside the cell: the cell spans the whole table, and on a phone that is wider than the screen, so a bare sentence would be centred over the part you have to scroll to. A sorted header gets its arrow and an underline; a checked row gets a wash, a filled box with a check, and aria-selected. The is-* classes only force a state for this page.

Anatomy

  1. Title (.tbl__title): names the table. The scroll region and the <table> both point at it with aria-labelledby.
  2. Frame (.tbl__scroll): a 2px frame, overflow: auto, focusable so keyboard users can scroll it (WCAG 2.1.1). Its ring sits outside the frame. While there is more to scroll toward the end, the frame is open on that side: the rows and the header bar run on past the edge, so the table never looks complete when the edge happens to fall between two columns. Scrolled to the end, it closes.
  3. Header bar: ink fill, uppercase labels (uppercase is structure). Sortable headers hold a .tbl__sort button whose whole cell is the target; it fills with paper on hover and focus, like a Button.
  4. Sort icon: a mask on the button's ::after: up and down arrows when unsorted, one arrow when sorted. With the underline that is two cues.
  5. Row name (<th scope="row">): sticky at the start edge, opaque, with a 1px rule that is a real border. It takes at most two thirds of the region and wraps between words (never inside one), so the next column always shows a real slice beside it.
  6. Numbers: data-align="end" right-aligns and turns on tabular, lining figures. While the region scrolls, a number column whose header is wider than its values starts them at the column's start (still right-aligned among themselves, so the decimals line up), so the edge cuts through values, never through blank cells.
  7. Row rules: 1px between rows, none after the last (the frame closes it). No zebra: nothing depends on telling two greys apart.
  8. Check column (optional): a 44px label around a 20px box, at every text size. Checked = filled with a check mark; some = a dash. On the ink header the box's frame is paper, so an empty "select all" reads as empty.
  9. Hint (.tbl__hint): shown by SG.table only while the region overflows. Its arrow points the way the table scrolls and sits on the first line of the sentence.

Accessibility

Table keyboard and screen reader behaviour
InteractionBehaviour
TabStops on the scroll region (so the keyboard can scroll it), then on each sort button, checkbox and link in reading order. The focus ring is inset on the ink header and stays clear of the sticky column (the region reserves room with scroll-padding, WCAG 2.4.11).
Enter / SpaceOn a sort button: sorts, then reverses. On a checkbox: toggles. Focus stays where it was.
Arrow keysWith focus on the scroll region, they scroll it. (Screen-reader table commands move cell by cell.)
Screen reader"Transactions, April, region", then "table with 7 rows and 5 columns". Headers are th scope; the sorted one announces "sorted descending". Sorting is announced ("Sorted by Amount, ascending") through the polite live region. A selected row announces "selected".
TouchEvery header and checkbox cell is at least 44px; rows are 44px. Sorting is a tap, not a gesture. The region scrolls with a swipe and with the keyboard.
Zoom / text sizeThe words grow; the 44px rows, the cell insets and the checkbox do not (they are chrome), so the room goes to the words, and a squeezed region tightens its side insets from 12px to 8px. At 320px or 200% text the table keeps its width and the region scrolls (tables are an exception to reflow, WCAG 1.4.10). Values stay on one line and no word is broken inside; the name column stays put and takes at most two thirds of the region (names wrap between words), so the values beside it are always partly in view.
Reduced motionThe only motion is the header fill and the checkbox lift; the lift's travel is multiplied by --move, so it becomes a plain fill.
Forced coloursFrame and rules become CanvasText; hover and focus on a sort button draw a 4px Highlight outline; checked boxes get a 4px frame; a selected row gets a 4px Highlight edge.
