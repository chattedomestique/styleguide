Dock

The dock is the app's main navigation: three to five places, at the bottom where a thumb rests. Each one is an icon and a word. One of them is lit, and says so to everyone.

When to use

Do

Use it for the three to five top-level areas of an app, the same on every screen and in the same order: Study, Decks, Stats, Profile. One short word each.

Don't

Use it for views of one screen (tabs), for a setting such as a date range (segmented control), or for where you are in a hierarchy (breadcrumb). Don't add a sixth item, hide the words to fit more, or put a destructive action in it.

Examples

The docks on this page are either in flow (data-position="static") or inside a preview frame, so none of them covers the page you are reading. In an app the default position: fixed floats the dock above the safe area. Click an item to move the lit one.

Floating pill

The default: a paper pill with a 2px frame. The current destination is a filled pill with a heavier word, and aria-current="page" tells assistive technology the same. A hover tints an item; a press fills it at once.

Compact

data-compact keeps the icon for every item but shows the word only for the current one, which widens into a pill. The other words are hidden visually; they stay in each link's name. Use it when width is short and the icons are universal; never as the place to start.

Words beat icons

Icon-only bars make people guess. Is the document icon "Statements" or "Invoices"? Is the lightning bolt "Activity" or "Shortcuts"? A visible word removes the guess, helps people with cognitive or low-vision needs, is what voice-control users say to tap an item (WCAG 2.5.3 Label in Name), and means the screen reader and the screen agree. It costs about 15px of height. Compact mode is for icons everyone already knows.

Keeping content clear of the dock

A floating dock covers the bottom of the page, and WCAG 2.4.11 says a focused control must never be entirely hidden behind it. The dock solves this by telling the page how tall it is: src/js/41-bars.js measures it with a ResizeObserver and publishes --dock-h, and the foundation uses it in two places:

  • .app__main gets bottom padding of the dock's height, the safe area and some air, so the last row can be scrolled fully above the dock.
  • html gets the same amount as scroll-padding-block-end, so when you Tab to a control or follow an anchor, the browser scrolls it clear of the dock instead of leaving it behind.

The frame below is a real, scrolling position: fixed dock inside a preview. It has contain: layout, which makes the frame (and not the window) the thing a fixed dock is pinned to, and data-chrome-scope, so --dock-h is published on the frame and not on this page. The page scrolls in <html> in a real app, where the foundation's scroll-padding does the work; this frame scrolls itself, so it repeats that one line. Tab into the list: each row scrolls into view above the dock, and the last one can be reached. Switch on Large text: the dock grows and the space follows.

In your app there is nothing to wire up: load styleguide.js, use .app and .app__main, and the dock reserves its own space. Without JavaScript a CSS estimate is used. On very short screens (landscape phones, large zoom) a floating dock stops floating and sits at the end of the page, as WCAG 1.4.10 advises.

In an app

<div class="app">
  <header class="appbar">…</header>
  <main class="app__main">…</main>
</div>
<nav class="dock" aria-label="Main">…</nav>   <!-- fixed, safe-area aware -->

Anatomy

  1. Container (.dock, a <nav>): a pill (floating) or a full-width bar, with a 2px frame. It floats --safe-bottom plus 12px above the screen edge and clears the notch at the sides. A canvas-coloured keyline keeps it apart from what scrolls beneath.
  2. Destination (.dock__item): a link or button, 56px tall, at least 44px wide. A 24px icon over a 13px uppercase word.
  3. Current cell: a filled pill with a heavier word, plus aria-current="page".
  4. Centre action (optional): a large circular button with an aria-label.
  5. Count badge (optional): a visible number, its meaning in screen-reader text.
  6. Safe area: --safe-bottom under the row, and at the sides.

Accessibility

Dock keyboard and screen reader behaviour
InteractionBehaviour
Tab / Shift+TabEach item is a tab stop, in visual order. It is ordinary navigation: no arrow-key model, no role="menu", no tablist.
Enter (link), Enter / Space (button)Go to the destination; run the action.
Screen readerA "Main" navigation landmark; "Study, link, current page". The count reads as part of the name: "Inbox, 3 unread". The centre action reads "Add transaction, button".
TouchEvery item is at least 44×44px (56px tall) with 4px between cells. No gesture is needed.
Zoom / text sizeIn rem. At 200% text the words wrap instead of clipping, the dock grows, and --dock-h follows. On very short viewports it stops floating.
Reduced motionNothing slides. In compact mode the current word fades in with no travel; the fill is a colour change.
Forced coloursThe dock and each item keep a border; the current item becomes Highlight with a 4px frame; the focus ring is a 4px Highlight outline.
  • Same items, same order, on every screen (WCAG 3.2.3 Consistent Navigation). Mark the current one; never hide the dock on sub-screens without a clear way back.
  • Give each dock on a page a unique label. An app has one aria-label="Main"; this page has several demos, so they are named differently.
  • Words are 13px, the smallest text the guide permits, so keep them short: they are uppercase with positive tracking.
  • The dock's contrast (its ink on its fill, and the current fill against the dock) comes from the tone roles that npm run test:contrast covers for every palette, theme and contrast mode.
