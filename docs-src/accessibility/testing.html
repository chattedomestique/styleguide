Testing

Five kinds of check, what each can and cannot catch, how to run them and how to extend them. Automated checks find a minority of accessibility problems. The rest needs a person and a device.

The tests read built files

The contrast test loads dist/styleguide.css; the other browser tests load docs/. After editing src/ or docs-src/, run npm run build first, or you are testing the old build. npm test starts with build:check, which only reports that the build is stale.

Setup

  • Node 20 or later, then npm install. The dev dependencies are axe-core and playwright-core; nothing else, and the guide itself has no dependencies.
  • A Chromium. The tests look for $CHROME_PATH, then the browser Playwright manages (install it with npx playwright-core install chromium), then /opt/pw-browsers/chromium.
  • Only Chromium is ever exercised. Firefox, Safari and every phone are outside the suite.
  • Never run two browser tests at the same time on a small machine; set A11Y_JOBS=1.
  • The repository's workflow (.github/workflows/ci.yml) runs the same commands: a static job first (lint, test:lint, build:check) and then a browser job (contrast, components, accessibility). A pull request runs the gate with --quick; a push to the main branch runs all five appearances.

Screenshots

Green tests do not prove a page looks right. Look at it at 320, 390 and 1024 px, in light and dark, with the default, mint and wire palettes and square and soft corners. Output goes to test-results/shots/; open the PNGs. Very tall pages are easier to read cut into pieces.

node tests/screenshots.mjs components/button.html --width 390
node tests/screenshots.mjs components/button.html --theme dark --palette mint --corners soft
node tests/screenshots.mjs components/button.html --width 320
node tests/screenshots.mjs components/button.html --matrix                    # 12 shots: light/dark x default/mint/wire x square/soft
node tests/screenshots.mjs index.html --selector '#use' --width 1280          # crop to one element

Other flags: --contrast more, --motion reduced|full, --forced-colors, --height, --scale (device pixel ratio) and --out. The tool saves the look through localStorage before the page loads, the same way a person's saved choice arrives.

The lint and its self-test

The lint is the owner's checker rebuilt on a real CSS tokenizer. The original matched prop: value; with regular expressions, so it missed a last declaration with no semicolon, a colour inside a custom property, a blur hidden behind a token, and any named colour. Its tooling audit fed it deliberate violations and it caught 44%. npm run test:lint replays those cases, and the current run reads violations caught: 111/135 (82%) · legitimate snippets passed: 33/33 · not static CSS/HTML (skipped): 15 · known misses: 24. The 24 misses are cases only a render can judge, such as a colour pair's contrast; npm run test:contrast judges those.

Errors fail the run. Warnings are printed and each should be explained in the change. Examples: a :hover outside a hover query, a physical property that breaks right-to-left, a fixed px size, an !important, uppercase outside a label, and, in the docs, a class that has no CSS yet.

What axe covers here

The gate runs axe-core (4.13.0 when this was written) with the tags wcag2a, wcag2aa, wcag21a, wcag21aa, wcag22aa and best-practice. On the Button page, 91 rules ran: 45 found something to check and passed, 45 had nothing to judge (no video, no frames, no image maps), and one, colour contrast, returned "needs review" results, which the gate does not report. Not run: seven experimental rules (css-orientation-lock, focus-order-semantics, hidden-content, label-content-name-mismatch, p-as-heading, table-fake-caption, td-has-header), three AAA or obsolete rules (color-contrast-enhanced, which the contrast matrix covers instead, identical-links-same-purpose, meta-refresh-no-exceptions) and the obsolete duplicate-id pair (the build checks ids).

Do not read a green run as "accessible"

The figure usually quoted is that automated tools find about a third of accessibility problems. Published estimates run from roughly 30 to over 50 percent, depending on whether you count issue types or occurrences. This project has not measured its own. Treat green as "nothing these tools know about is wrong".

Only a person or a device finds these

  • Meaning. Whether a label, alt text, error message or heading is actually helpful and correct. Whether reading order and focus order make sense. Whether instructions rely on shape, colour or position.
  • What assistive technology says. VoiceOver, TalkBack, NVDA and JAWS announcements. Whether a live region is really spoken. Rotor and heading navigation. Voice Control ("tap Save") and Switch Control.
  • The platform. Safari and WebKit behaviour. Installed iOS apps and their safe areas (WebKit bug 301994). Dynamic Type and Android font scale. A keyboard covering a field. iOS zooming on focus. Gestures that fight the system back gesture. Thumb reach.
  • Perception. Colour-only cues (use the wire palette and the browser's vision-deficiency emulation). Motion comfort. Glare outdoors. Flashing.
  • Feel. Whether a press answers at once. Accidental activation. Whether a drag alternative is discoverable. Hover content that behaves.
  • Layout under stress. 400% zoom, 256 px-tall viewports, text spacing overrides, landscape phones, right-to-left, long translated strings. The gate sees scrolling and cut-off text in a clipping frame; it does not see text that overlaps.
  • Content. Language of parts, plain language, consistent names and help, cognitive load.

The scripts for these are on Manual. Nobody has run them yet.

The appearance matrix

A page is tested in several looks, because most accessibility bugs are "fine in the default, broken in one other setting".

The five appearances the accessibility gate runs
AppearanceSettingsWidthWhy this one
defaultDevice defaults: light, default palette, square corners390What most people see. Reflow at 320 px and at 200% text is measured here, once, with every <details> open.
dark-mint-softDark, mint, soft corners390Dark colours, a coloured accent, and the soft radius roles (the inset focus ring meets the curve).
wire-squareLight, wire, square corners390Zero chroma: anything that relied on colour shows up.
contrast-periwinkle-darkMore contrast, periwinkle, dark1280The higher-contrast knobs, and the wide layout.
forced-colorsWindows High Contrast emulated, otherwise default390Backgrounds and shadows are removed. Every control must keep a border and a focus outline. axe's colour-contrast rule is switched off here.

--quick runs only the first two. The contrast matrix is separate and wider: light and dark × normal and more contrast × all six palettes (24 combinations, 5,400 checks), covering every role pair, every tone in pastel and bold (the tones are discovered from the CSS, so a new one is tested the day it exists), the focus ring on every surface, the scrims over a white photo, and that the device's "more contrast" request and data-contrast="more" produce identical colours. The screenshot tool's --matrix takes 12 pictures at 390 px.

Not in any automated matrix: the sand and cream palettes in the gate (the contrast matrix does cover them), reduced motion in the gate (specs emulate it per element), text at 200% in dark or forced colours, right-to-left beyond the specs that mirror, landscape, and every browser except Chromium.

Reading the reports

Both browser tests exit non-zero on any error and write JSON to test-results/, which is not committed. The terminal shows the first six errors per page and appearance; the JSON has all of them.

a11y.json

An array with one entry per page and appearance:

{
  "page": "components/button.html",
  "appearance": "default",
  "errors": [],
  "warnings": [],
  "tabStops": 53
}

tabStops is how many Tab stops the walk reached (capped at 120). An unexpectedly low number means controls are unreachable or the page broke. Error lines begin with what found them:

  • axe <rule> (impact, Nx) with the selector and axe's explanation.
  • focus: a control that shows no outline or shadow when focused, a ring under 3:1 against what it is drawn on, or a control covered by other content.
  • target WxH: an element under 24 px (error). Under 44 px is a warning.
  • forced-colors: a control with no border once backgrounds are removed.
  • reflow@320 and reflow@200% text: sideways scrolling, with the elements that stick out. clipped@320 and clipped@200% text: text cut off by a clipping frame.
  • console: an uncaught error or a failed request. runner: the test itself broke.

This is the terminal output for a page broken on purpose (a scratch copy of the docs with one extra page, not part of the repository), in the default appearance:

x 6 error(s)              bad.html  [default]
      x axe button-name (critical, 1x): Buttons must have discernible text  e.g. button[data-shape="circle"] :: Element does not have inner text that is visible to screen readers
      x axe color-contrast (serious, 1x): Elements must meet minimum color contrast ratio thresholds  e.g. p :: Element has insufficient color contrast of 2.13 (foreground color: #aaaaaa, background color: #f5f5f5, ...). Expected contrast ratio of 4.5:1
      x focus: no visible focus indicator on button.btn "No ring"
      x target 16x16: a "x" is under the 24px WCAG 2.5.8 floor
      x reflow@320: horizontal overflow 176px. div right=496 (viewport 320)
      x reflow@200% text: horizontal overflow 122px. div right=512 (viewport 390)

Useful one-liners (jq is optional; Node's require('./test-results/a11y.json') works too). All four were run against real reports:

# a11y: every failing page and appearance, with its errors
jq -r '.[] | select(.errors | length > 0) | "\(.page) [\(.appearance)]", (.errors[] | "  " + .)' test-results/a11y.json

# a11y: the distinct warnings across the whole run
jq -r '[.[].warnings[]] | unique[]' test-results/a11y.json

# a11y: how many Tab stops each page reached (0 or 1 usually means something is wrong)
jq -r '.[] | "\(.page) [\(.appearance)] tab stops: \(.tabStops)"' test-results/a11y.json

# contrast: one line per failed check
jq -r '.failures[] | "\(.key)  \(.fg) on \(.bg)  \(.ratio * 100 | round / 100):1 (needs \(.min))  \(.what)"' test-results/contrast.json

Add a colour pair to the matrix

A role that is used as text or as a control boundary and is not listed in tests/contrast.mjs is unverified. When you add a role (declared in src/tokens, with a comment), add its pairs in the same change:

// tests/contrast.mjs, inside buildPairs(), next to the other add() lines:
//        foreground role     background role       floor  label for the report           floor in higher contrast
add('--ink-mute', '--accent-soft', 4.5, 'placeholder on soft accent', 7)

// Pairs that only exist inside a tone or status scope go in TONE_PAIRS instead:
//   { fg: '--tone-ink-soft', bg: '--tone-bg', min: 7, bold: 6.5, what: 'tone secondary text' },
// `min` is the pastel floor, `bold` the floor under data-emphasis="bold". Add child: true to read the
// pair on a child of the toned element (the --surface-* roles and --focus are read that way).
  1. Arguments of add(): foreground role, background role, the floor, a label for the report, and (optional) the floor under data-contrast="more". Use 4.5 for text and 3 for boundaries and icons; 7 for body text.
  2. npm run build, then npm run test:contrast. Each pair adds one check per theme, contrast and palette combination (24). Checked: the pair above passes (5,424 checks instead of 5,400).
  3. If it fails, change the knobs or the role, not the floor. Lowering a number needs a reason written next to it.
  4. A new palette goes in the PALETTES list at the top of the file. A new tone is found from the CSS on its own.

Write a component spec

axe cannot know that arrow keys should move between tabs. A spec can. One file per element in tests/components/<name>.mjs, exporting tests. This one tests the docs shell itself, and was run against it:

// tests/components/shell.mjs: the docs shell's own skip link, mobile menu and reduced-motion token.
export const tests = [
  {
    name: 'skip link is the first Tab stop and moves focus to <main>',
    async run({ page, goto, expect }) {
      await goto('index.html')
      await page.keyboard.press('Tab')
      await expect.focused(page, '.skip-link', 'first Tab stop')
      await page.keyboard.press('Enter')
      await expect.focused(page, 'main#main', 'focus lands in main')
    },
  },
  {
    name: 'menu button toggles aria-expanded; Escape closes and returns focus',
    viewport: { width: 390, height: 844 }, // the drawer only exists below 64em
    async run({ page, goto, expect }) {
      await goto('index.html')
      await expect.attr(page, '.docs-bar__menu', 'aria-expanded', 'false')
      await page.locator('.docs-bar__menu').focus()
      await page.keyboard.press('Enter')
      await expect.attr(page, '.docs-bar__menu', 'aria-expanded', 'true')
      await expect.focused(page, '#docs-nav a', 'focus moves into the drawer')
      await page.keyboard.press('Escape')
      await expect.attr(page, '.docs-bar__menu', 'aria-expanded', 'false')
      await expect.focused(page, '.docs-bar__menu', 'focus returns to the trigger')
    },
  },
  {
    name: 'reduced motion turns travel off (--move is 0)',
    reducedMotion: true, // emulates prefers-reduced-motion: reduce
    async run({ page, goto, expect }) {
      await goto('index.html')
      const move = await page.evaluate(() => getComputedStyle(document.documentElement).getPropertyValue('--move').trim())
      expect.equal(move, '0', '--move under reduced motion')
    },
  },
]
  • The test object: name; optional viewport (default 390 × 844), touch (true turns on touch emulation) and reducedMotion (true emulates prefers-reduced-motion: reduce); and run({ page, goto, expect, url, browser }).
  • page is a Playwright page. goto('components/x.html') opens a built docs page and turns off smooth scrolling. expect has ok, equal, focused(page, selector) and attr(page, selector, name, value), and in the current harness eventually(read, test, msg), which polls until a condition holds: use it instead of a fixed wait for anything that settles after an event. Anything else, throw.
  • The harness starts each test with empty localStorage and fails it if the page logs an error or throws.
  • What every spec should cover: Tab reaches it; each documented key does what the docs table says; the aria-* state flips together with the visible state; Esc closes an overlay and focus returns to its trigger; for anything pressable, --lift and --fill in each state (see tests/components/button.mjs); nothing throws.
  • Run it with npm run test:components -- name.

CI

The repository's workflow runs the commands above as separate steps so that a failure names its step:

static    npm ci, npm run lint, npm run test:lint, npm run build:check
browser   (after static) npm ci, install Chromium, npm run build, npm run test:contrast,
          npm run test:components, npm run test:a11y  (--quick on a pull request), A11Y_JOBS=2
          and the test-results folder uploaded when anything fails
  • build:check assumes dist/ and docs/ are committed, which they are. If you fork and do not commit them, replace that line with npm run build.
  • The Chromium download is the slow step. Cache ~/.cache/ms-playwright keyed on package-lock.json if it matters.
  • Manual passes cannot be automated. Put "manual pass done for this release" in your release checklist (Upgrade).

Lighthouse and PWA checks

Do not make a Lighthouse PWA score a release gate. Chrome's own documentation says so:

"PWA testing in Lighthouse is deprecated. For more information on its deprecation see Chrome's updated Installability Criteria."

Chrome for Developers, Lighthouse: installable manifest, read on 30 September 2026

  • Check installability in DevTools: Application, then Manifest and Service workers. Chrome no longer requires a service worker to offer install, and Safari on iOS needs neither a manifest nor a worker (PWA).
  • Lighthouse's accessibility category runs axe-core, so it adds nothing to the gate above, only a score that hides the detail.
  • Nothing in this repository runs Lighthouse.

Emulating preferences while you work

Chrome DevTools, Rendering panel: emulate prefers-color-scheme, prefers-contrast, prefers-reduced-motion, forced-colors and vision deficiencies. Or use the Appearance panel at the top of this site, which sets the same attributes the device would. Emulation is a shortcut for development; it does not replace the device scripts on Manual.
