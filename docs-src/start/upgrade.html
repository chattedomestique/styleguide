Upgrade

Coming from the original Flashcards style sheet, how versions work, what a release is allowed to break, and how to move an app from one to the next.

Where things stand

The version is 0.2.0 (package.json). The repository has no git tags and nothing is published: private: true keeps it off npm. The changelog is STYLE.md §8; there is no separate CHANGELOG.md. Nothing has been upgraded from one release to another yet, so the update steps below are the policy and a recipe, not something anyone has done twice.

From the Flashcards style sheet v0.1

This guide is your sheet, generalised. It was re-founded on it rather than patched: your type, space, line, shape, hit-target and focus tokens, your role names, the tone API, the .card element and its classes, the gates and the checker's rules are kept as you wrote them. What was wrong with the original, and what was done about each finding, is on the Audit page.

Your app already has a .card

This is the migration note from the original sheet's README.md, as the owner wrote it:

../styles.css already owns .card, .card-inner and .card-face, so the two can't load together as they stand. Its canvas is cream with a dotted background, Space Grotesk, 4px borders, a 10px hard shadow and a 26px radius; none of that is carried into this sheet.

When the app adopts the sheet: load design/css/flashcards.css, remove or rename the old .card* rules, map --t1…--t6 to --tone-1…--tone-6, and move the flip onto .card--study at gate 4 (the rules in the root README still stand). Or prefix the new classes first and migrate at leisure. The prefix is an open decision.

Two things have moved since. This guide answered the prefix question by keeping your short names and adding no prefix (the audit lists it as a decision you may still want to make), so the old rules are the ones that move aside. And the collision is wider than .card. Checked against the tokens and classes that the audit lists for the app's styles.css:

Names that the app's styles.css and this guide both define

Classes.app, .card, .sr-onlyThe rule that comes later or is unlayered wins, property by property. The app's .card has a 4px border, a 26px radius and a 10px shadow.

The app's other names (.deck, .card-inner, .card-face, .dots, --t1 to --t6, --radius, --gap and so on) do not exist in the guide and cannot collide. An earlier build of the app had .btn, .toast, .chip and .skip-link; if your copy still does, they collide too.

Versioning policy

Semantic Versioning: MAJOR.MINOR.PATCH. The "API" is what an app can depend on, listed in the next section.

Which kind of change bumps which part of the version
BumpChanges that cause it
MajorRenaming or removing anything in the API list below. Changing what an attribute value means. Changing documented markup so that an app's HTML must change. Raising the browser floor (today light-dark(): Chrome and Edge 123, Firefox 120, Safari 17.5, plus container queries, :has(), @property, color-mix() and cascade layers).
MinorNew tokens, elements, variants, palettes, tones, icons or SG functions. Retuning colour or size values while every check in npm run test:contrast and the accessibility gate still passes. Deprecating a name (it keeps working).
PatchBug fixes, contrast and focus fixes that do not change a name, documentation, tests, and anything an app cannot see.

While the version is 0.x, Semantic Versioning treats the API as unstable. The rule here: a breaking change bumps the minor number and is listed as breaking in the changelog. From 1.0.0 on, breaking changes bump the major number. The 1.0.0 release is a decision, not a date.

Accessibility fixes are the one thing that can change looks in a patch release: if a pair fails a check it is corrected without waiting for a minor bump, and the changelog says when that happened.

Update an app

  1. Read the changelog (STYLE.md §8) from your version to the new one. Start with anything marked breaking.
  2. See exactly what changed in the CSS by comparing the two unminified files: 
    diff -u old/styleguide/styleguide.css new/styleguide/styleguide.css | less
  3. Replace the guide's files wholesale. Swap the whole styleguide/ folder, or change the tag in the jsDelivr URLs. Never patch files in it by hand; your overrides live in your own CSS (Customize).
  4. Find uses of anything renamed or removed. This is the search for the names on this page: 
    grep -rnF -e '.card--study' -e '.card__answer' -e '--ratio-study' -e '--grey-' my-app/ --include='*.css' --include='*.html' --include='*.js'
  5. Bump your service worker's cache name (or the versioned folder name) so installed copies fetch the new files. Without this a cache-first worker keeps serving the old CSS (PWA).
  6. Look at your screens. The guide's tests cover the guide's own pages, not your app. Open each main screen in light and dark, in a palette you do not use every day, at 320 px wide and with text at 200%, and run anything the changelog touches from the manual pass.
  7. Deploy. To go back, put the old folder or tag back.

Deprecating a name

Before removing or renaming a token or class, keep the old name working for one release as an alias of the new one, so apps get a warning period instead of a broken screen, and list it as deprecated in the changelog with the version it goes away in. .card--study and .card__answer are this convention in use. (--ratio-study was renamed without an alias.)

Changelog convention

  • The changelog lives in STYLE.md §8, newest version first. A version heading names the date; each entry names the exact token, class, attribute or function in code font; breaking changes say what to do instead.
  • Changes to contrast numbers, focus behaviour or keyboard behaviour are always listed, even when tiny. They are what an app's own accessibility pass depends on.
  • The version has one source, package.json. The lint fails if the version on STYLE.md's third line disagrees with it.

Cut a release (maintainers)

In order. The version bump comes before the build, because the version is written into the banner of dist/ and into the docs header.

npm version --no-git-tag-version minor     # edits package.json and package-lock.json only
# edit STYLE.md: the version on line 3, and a new entry in section 8
npm run build                              # the banner and the docs header pick up the new version
npm test                                   # build:check, lint, contrast, components, accessibility
git add -A
git commit -m "Release 0.3.0"
git tag -a v0.3.0 -m "0.3.0"
git push --follow-tags
  • What was run: in a scratch copy, the version bump, npm run build (the banner read /*! styleguide v0.3.0), build:check (passed) and the lint, which failed with "STYLE.md says v0.2 but package.json is 0.3.0" until STYLE.md is edited. The tag and the push were not run.
  • Never move or re-create a tag. jsDelivr caches a tag as immutable. A fix is a new patch version.
  • jsDelivr needs no publish step. It serves any tag of a public GitHub repository (Install).
  • dist/ and docs/ are committed on release, so every tag is linkable and GitHub Pages can serve docs/. Do not commit them from a feature branch; run npm run build when you release.
  • Which version an app has: the first line of its styleguide.css or styleguide.min.css.
