Contributing

The guide grows one element at a time, from example screens the owner sends. This page is the whole routine: how a screen becomes an element, the words to hand an agent, what a pull request must show, and the four small extensions (a palette, a tone, an icon, a corner style) that need no new element.

The loop

  1. A screen arrives. An image, or pasted HTML and CSS. A link that cannot be opened (a login wall, a 403) does not count; see References.
  2. It is analysed, not copied. Measure it, list its parts, compute its contrast, and write the notes to references/screens/.
  3. Each idea is sorted: already covered by an existing element (use that), worth a new element (build it), or left behind (say why). The rules in Why things were left behind decide most of it.
  4. A new element goes through the gates, in order. Colour before structure hides layout problems.
  5. The pull request shows its evidence, and updates Status, Changelog and References.

Before anything else, read CLAUDE.md (the rules and the commands) and STYLE.md (the exact values and their reasons). They are law; this page only orders the work.

The gates

The owner's sheet moves every element through six gates. Do not skip ahead. The table is the same one CLAUDE.md carries; Status records where each element stands, and the Checklist is the definition of done for one element.

The six gates: the question each asks and when it is closed
GateQuestionClosed when
0 BriefWhat is it for, who presses it, what is the one idea?One sentence, at the top of the docs page.
1 WireframeDoes the structure work in data-palette="wire"?The squint test passes: colour is not hiding a layout problem.
2 StatesRest, hover, focus, pressed, selected, disabled, busy, error: all defined?Every state sets --lift and --fill, and nothing else.
3 ColourRoles only, tones, contrast verified?npm run lint and npm run test:contrast are green.
4 MotionOne transition; is reduced motion gentler?The spec passes with reducedMotion.
5 FreezeIs it finished?Docs complete, the accessibility gate green, screenshots reviewed, and the owner has signed it off.

Step by step

  1. Scaffold. npm run new:component -- name --order 45 writes the CSS, the docs page and a spec stub, and refuses to overwrite anything. Orders are ranges: actions 10 to 19, forms 20 to 39, selection and navigation 40 to 59, surfaces 60 to 79, overlays and feedback 80 to 99, data 100 to 119, media and tools 120 to 139.
  2. Copy the structure of src/components/button.css. --lift and --fill, private --_* properties, variants through data-*, states through ARIA, @layer sg.components, the hit area, the focus ring, the hover gate, forced colours, reduced motion. Build on Card for containers instead of a parallel surface. If the element reads another element's private properties, as Select does Input's, the build records that in dist/elements/manifest.json as buildsOn, so say so in the file header.
  3. Write real HTML in the docs demos. The "Markup" disclosure is read from the live demo, so the page cannot drift. Include when to use (do and don't), every variant and size, every state, an example in context, the anatomy, an API table, a keyboard and screen-reader table, and the tokens used. Copy comes from an app: decks, wallets, tasks, streaks.
  4. Add script only if HTML and CSS cannot do it. src/js/NN-name.js (name it after its element, and the build's manifest attaches it to that element), an IIFE on window.SG, event delegation on data-sg-* hooks, progressive enhancement, SG.announce() for changes that move no focus, SG.motion.reduced() before animating from script.
  5. Write the spec in tests/components/name.mjs: keyboard, ARIA flips, focus return, and the --lift and --fill states. Follow the WAI-ARIA Authoring Practices pattern exactly; Patterns lists which element follows which, and Testing shows how to write the spec.
  6. Verify, then look. 
    npm run build
npm run lint
node tests/components.mjs name
npm run test:a11y -- --pages components/name.html
node tests/screenshots.mjs components/name.html --width 390 --theme dark --palette mint --corners soft
    Green tests do not prove it looks right. Open the screenshots at 320, 390 and 1024 pixels, light and dark, in the default, mint and wire palettes, with square and soft corners (--matrix renders the grid, --selector '#examples' crops). Fix what looks wrong, not only what fails. What each command can and cannot catch is on Testing.
  7. Move the status. Update the table in Status and in STYLE.md section 6, and add a line to the Changelog and STYLE.md section 8.

The prompt to give an agent

Paste this, and attach the screens. The square brackets are for you to fill in; everything else is the job as the repository defines it. It asks for the same thing every time, so the results can be compared.

You are adding what is shown in the attached example screen(s) to the style guide in this repository. Work on a branch and commit as you go. Do not push or open a pull request until I say so.

READ FIRST, completely, before you change anything:
- CLAUDE.md (the rules, the commands, the pipeline) and STYLE.md (the exact values and the reasons). They are law.
- src/components/button.css, docs-src/components/button.html and tests/components/button.mjs: the reference element. Copy its structure. Then src/components/card.css, the owner's original.
- docs-src/project/decisions.html: what is settled and what is still open. Do not reopen a settled one without saying why.
- docs-src/components/: the elements that exist. Reuse before you invent.

THE SCREEN(S)
[Attach the images, or paste the HTML and CSS. If a link could not be opened, say so and ask me for the source. Never guess from a title.]
What it is for: [the app and one line about it]
What I like: [...]
What to avoid: [...]

STEP 1. ANALYSE. DO NOT COPY.
Save the notes as references/screens/imgN-short-name.md (N is the next free number). Include: an inventory of every screen and element; the palette, sampled from pixels (say which values are estimates); the contrast of every text, icon and boundary pair, computed with the WCAG formula; radii, borders, shadows, spacing, sizes and touch targets; the type; each component's anatomy and states; what is generic and what is one-off decoration; every accessibility problem; and what you could not measure.
Do not copy their colours, radii, shadows, gradients or copy. Mockups usually fail contrast and break the seven rules. Take the idea and the anatomy, and build it from roles and the owner's vocabulary.

STEP 2. SORT THE IDEAS.
For each idea write one line: already covered by an existing element (name it), new element (name it, with the owner's short style of naming), or left behind (and the reason). Do not invent a second way to do something the sheet already decided: no second type family, no third line weight, no fourth radius.

STEP 3. BUILD EACH NEW ELEMENT THROUGH THE GATES, IN ORDER.
npm run new:component -- name --order N (actions 10-19, forms 20-39, selection and navigation 40-59, surfaces 60-79, overlays and feedback 80-99, data 100-119, media and tools 120-139).
Gate 0 brief: one sentence on the docs page. Gate 1 wireframe: it works with data-palette="wire". Gate 2 states: rest, hover, focus, pressed, selected, disabled, busy, error, each only setting --lift and --fill. Gate 3 colour: roles only. Gate 4 motion: one transition, travel multiplied by --move, reduced motion gentler and never instant. Gate 5 freeze: docs complete, accessibility gate green, screenshots reviewed.
Rules that catch people out:
- Only src/tokens contains a colour literal. Radii are only --radius-card, --radius-tile, --radius-ctl and --radius-pill. Line widths are --bw, --bw-thin, --bw-heavy or --ring.
- State comes from ARIA and native attributes, never from classes. The is-* classes only force a state in the docs and the specs.
- A shadow is hard-edged and means "you can press this". Nothing else gets one. No gradients, no blur, no text-shadow, no !important, no transition: all.
- Never colour alone: selected, on, error and status always have a second cue. Never opacity on text.
- Every tappable thing has a 44px hit area (the ::after pattern in button.css), 8px between targets. Every icon-only control has an aria-label. Every gesture has a click or key equivalent.
- Native elements first. Roving tabindex, Esc and focus return as in the WAI-ARIA Authoring Practices.
- rem for sizes, logical properties for direction, hover gated by @media (hover: hover), symbols as icon masks and never text glyphs or emoji.
- Copy in the docs comes from an app (decks, wallets, tasks, streaks), never placeholder text.
- If a role or token is missing, add it in src/tokens with a comment and a line in tests/contrast.mjs. Do not inline a colour.
- Never edit dist/ or docs/ by hand. Run npm run build.

STEP 4. VERIFY, THEN LOOK AT IT.
npm run build, npm run lint, npm run test:lint, node tests/components.mjs name, npm run test:a11y -- --pages components/name.html, and npm run test:contrast if you touched a colour. Then run node tests/screenshots.mjs on every page you made at 320, 390 and 1024 pixels, light and dark, in the default, mint and wire palettes, square and soft corners, and open the images. Fix what looks wrong, not only what fails. Do not silence a failing check: fix the cause, or change the rule with the reason written down.
When the checks are green, run npm run build one last time and commit the regenerated dist/ and docs/ with your source. CI runs npm run build:check and fails when they are stale.

STEP 5. REPORT, plainly.
- What you built: class names, data attributes, docs pages.
- The exact commands you ran and what each printed at the end.
- What is untested or weak. Tests run in Chromium only; say so, and say what a person still has to try on a real phone.
- What you took from the screens and what you left behind and why. Add it to docs-src/project/references.html.
- Status and Changelog: update docs-src/project/status.html, docs-src/project/changelog.html, and STYLE.md sections 6 and 8.
- Anything you needed in src/tokens, src/base, src/layout or scripts that you did not change, as a request.

Pull request checklist

Put this in the description of every pull request that adds or changes an element, and tick what is true. Anything you could not do goes in the description in words, not as a silent blank.

- [ ] npm run build was run, and the generated dist/ and docs/ are committed with the source (npm run build:check passes; CI runs it)
- [ ] npm run lint has no errors; each warning and each lint-allow waiver is explained
- [ ] npm run test:lint passes (add a case to tests/lint-cases.json when you add a lint rule)
- [ ] npm run test:contrast passes (required if a colour, a tone or a palette changed)
- [ ] The spec in tests/components/ passes, and covers keyboard, ARIA flips, focus return and --lift / --fill
- [ ] npm run test:a11y passes for each new page in all five appearances (CI runs two on a pull request, so run the rest yourself)
- [ ] Screenshots reviewed at 320, 390 and 1024 px; light and dark; default, mint and wire; square and soft corners; high contrast
- [ ] Squint test: it reads in data-palette="wire". Cover the logo: it could not be any product.
- [ ] Roles only, no literals; no !important, gradients, blur or transition: all
- [ ] Looks right in square and soft corners with no corner-specific code
- [ ] 320 px and 200% text do not clip or scroll sideways
- [ ] Keyboard follows the WAI-ARIA pattern; focus ring visible on tones and on ink; Esc and focus return for overlays
- [ ] Names, roles and states exposed; icon-only controls labelled; a live region for changes with no focus move
- [ ] Targets 44 px or more with 8 px between; every gesture has a tap or key equivalent
- [ ] State is never colour alone; a real border exists for forced colours
- [ ] Reduced motion: no travel, nothing instant, nothing bouncing
- [ ] Docs page complete: when to use, variants, states, in context, anatomy, API, keyboard and screen reader, tokens; links and anchors resolve
- [ ] References updated (what was taken, what was left behind and why), if the work came from a new screen
- [ ] Status updated (Project page and STYLE.md section 6) and Changelog updated (Project page and STYLE.md section 8)
- [ ] Anything not tested, and every known limit, is written in this description

Adding things

These four extensions need no new element. Each one ends with the build, the gate and a look.

A palette

  1. In src/tokens/40-palettes.css, copy a block such as [data-palette="mint"] and rename it. It sets knobs only, never a colour: --k-neutral-h and --k-neutral-c (the grey's tint), --k-canvas-l and the canvas chroma, --k-accent-h and --k-accent-c, and a hue and vividness for each of the six tone slots (--tone-h-1, --tone-c-1, and so on up to 6).
  2. A light accent, like cream's yellow, needs dark text on it: set a dark --k-on-accent-* and --k-accent-ink-*.
  3. Add the name to PALETTES in tests/contrast.mjs and to OPTIONS.palette in docs-src/assets/docs.js, so the appearance panel offers it. The Colour page lists the palettes; add it there too.
  4. npm run build && npm run test:contrast. Customize walks through a worked palette that passes the matrix. Every pair is checked in a real browser in every theme and contrast mode. Lightness gaps are fixed by the shared knobs, so a palette that only moves hue and chroma cannot break contrast; if it does, the knobs are wrong, not the test. Then screenshot a few pages with --palette name.

A tone

The six numbered slots are the API and stay six: a palette decides each slot's hue, which is the first bullet here.

  • A slot's hue. Set --tone-h-N (hue) and --tone-c-N (vividness, 0 is grey) inside a palette block. The pastel fill, its text and its soft text are derived, and each pair clears 7:1; the text on the solid pill clears 4.5:1.
  • A new status tone (beyond ok, warn, bad and info). In src/tokens/20-tones.css add a --hue-name beside --hue-ok, add a [data-tone] rule for your name that sets --th and --tc, copying the four beside it, and add the selector to the :is(…) list that computes --tone-bg and --tone-ink. Add the name to TONES in tests/lib/rules.mjs, or the lint will call your new value a typo. tests/contrast.mjs reads tones from the built CSS, so run npm run build first and it is tested. Status always carries an icon or words as well as the colour, so Tag needs a symbol for it.
  • Tones carry rhythm, never meaning. A tone alone must not say "error".

The roles and their maths are on Tones.

An icon

  1. Drop a 24 by 24 stroke SVG in src/icons/. The file name is the id: bell.svg becomes ic--bell. The viewBox must be 0 0 24 24 (the build refuses anything else), and the drawing is stroke-only: the build re-strokes every icon at 2px with square caps, so the file's own stroke settings do not matter. Lucide icons (ISC) are welcome; keep src/icons/LICENSE-lucide.txt beside them.
  2. Use it as <span class="ic ic--bell" aria-hidden="true"></span>. The build fails on any page that uses an icon class with no file behind it, which is the typo check. Size it with --ic-size.
  3. npm run build writes it into dist/icons.css. The owner's five drawings (arrow, plus, minus, close, check) are in the main bundle; every other icon needs icons.css.
  4. An icon never replaces a word. A control whose only content is an icon gets an aria-label on the control, not on the icon. See Icons.

A corner style

  1. In src/tokens/30-corners.css add a block such as [data-corners="name"] that sets the three roles and nothing else: --radius-card, --radius-tile and --radius-ctl. Circles and pills stay --radius-pill. Components must not change, and the lint refuses any radius that is not a role.
  2. Add the value to OPTIONS.corners in docs-src/assets/docs.js so the appearance panel offers it.
  3. Look at Card, Dock, Sheet, Field and Tabs with --corners name. Watch for a focus ring clipped by a large radius, and remember one shape gesture per card: round it or notch it, never both. The notch card stays square.

A token or a role

Declare it in src/tokens/ with a comment saying what it is for, document it in STYLE.md section 2, and, if it is a colour pair, add a line for it in buildPairs() in tests/contrast.mjs (a pair read inside a tone goes in TONE_PAIRS). A role that is used as text or as a boundary and is not listed there is unverified. The lint's drift check fails if CLAUDE.md, STYLE.md or README.md name a token or class that does not exist.

When the lint is wrong

Do not silence a failing check. Fix the cause, or change the rule with the reason written down. If a line is legitimately outside a rule, waive that one line with a reason the next reader can judge: /* lint-allow rule: why */ on the line or the one above, or lint-allow-file for a whole file (<!-- lint-allow-file colour: why --> in a docs page). Every run lists the waivers it honoured, so an exception is allowed and never invisible.

Do not

  • Do not edit dist/ or docs/ by hand. Edit src/ and docs-src/, then run the build.
  • Do not add runtime dependencies or a bundler. package.json holds dev tooling only.
  • Do not use !important (except [hidden] and .sr-only), transition: all, outline: none without a replacement, a tabindex above zero, user-scalable=no, a div with role="button", gradients, blur or text-shadow.
  • Do not copy CSS from a reference design. Copy the idea, and build it from roles.
  • Do not invent a second way to do something the owner's sheet already decided.
  • Do not claim what was not tested. Tests run in Chromium only; say so.
