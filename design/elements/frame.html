Frame

The shell every screen sits in: the bars, the one region that scrolls, and the safe areas, so the content inside never has to know there's a notch.

01

Anatomy

A grid of three rows, and a column beside them on a wide screen. Only the scroll region scrolls. Each bar pads its own safe area; the frame pads only the edges no bar covers.

  1. 1
    Frame.frame

    A grid: top bar, scroll region, bottom bar. As tall as the dynamic viewport (100dvh), or as its parent when the parent has a set height (a device, a pane). A container, so --gutter follows the frame's own width.

  2. 2
    Top slot.frame__top

    Row one. The Top bar wears it and pads the status bar itself. With no top bar the frame keeps a band the height of the status bar, so nothing scrolls under the clock.

  3. 3
    Scroll region.frame__scroll

    The app's <main> and the only scroller. Content is stacked 32px apart, padded to the gutter or the safe area, whichever is wider, with scroll padding so a focused thing stops clear of the bars.

  4. 4
    Bottom slot.frame__bottom

    Row three. The Tab bar wears it, or, in a focused task, it holds the action row and the frame pads it. With no bottom bar the scroll region pads the home indicator.

  5. 5
    Side slot.frame__side

    Wide only (2.4): a column beside the other three, for the Sidebar. It folds away under 45rem of frame.

How spaced repetition works

Each card comes back just before you'd forget it. Get one right and it waits longer next time: a day, then three, then a week. Get it wrong and it comes back tomorrow.

So a session is short. Today's seven cards in Shapes take about three minutes, and the ones you already know stay out of the way until they're due again.

A streak counts the days you finished what was due. Miss a day and nothing is lost: the cards wait, and tomorrow's session is a little longer.

04

Usage

  1. Do

    One frame per screen, as the first thing in <body> after the skip link, with the scroll region as the <main>. Keep the order top bar, content, bottom bar, so Tab goes the way the eye does. Load dist/flashcards.js for --chrome.

  2. Don't

    Don't let the page scroll behind the frame, read --safe-* in content, or float a bar over the content: bars run edge to edge and clip what scrolls. Don't use position: fixed inside the frame for overlays; a dialog, sheet or menu goes in the top layer (<dialog>, popover).

  3. Installed PWA

    Needs viewport-fit=cover, or every safe area is 0, and interactive-widget=resizes-content, so Android ends the frame at the keyboard. The frame is the one thing sized in dvh; the page never scrolls, so the browser's bars stay put in a tab too. While the keyboard is up the Tab bar hides (frame.js sets data-keyboard), so the field has the room.

  4. Mac and SwiftUI

    In a Mac window the toolbar and sidebar are the system's, so the content is a frame with no bars (see Screens). In SwiftUI the frame is the scene: NavigationStack or NavigationSplitView with .safeAreaInset(edge:) for an action row.
